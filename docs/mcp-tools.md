# MCP tools

When lumine-mcp is connected, jupyter-repl publishes tools for the kernels already running in this window. Tools require explicit kernel and notebook identities; they do not choose the active kernel, open a kernel picker, or start a new interpreter.

| Tool                      | Input                                                        | Result                                                                                                      |
| ------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| ListJupyterKernels        | No arguments.                                                | Kernel IDs, language, state, execution count and associated files.                                          |
| ExecuteJupyterCode        | kernelId, code, operationId.                                 | Acceptance receipt and executionId; results use the kernel's normal output log.                             |
| RunJupyterCell            | kernelId, notebookId, cellId, expectedRevision, operationId. | Runs the captured cell through its normal notebook output pipeline.                                         |
| BindJupyterNotebookKernel | kernelId, notebookId, expectedRevision, operationId.         | Binds an existing kernel through the normal notebook transaction; completion includes the updated revision. |
| RunJupyterNotebook        | kernelId, notebookId, expectedRevision, operationId.         | Runs captured code cells sequentially, stopping on the first failure.                                       |
| GetJupyterExecution       | executionId; optional waitMs and afterVersion.               | State, cell progress, execution counts, bounded output summaries and MIME metadata.                         |
| InterruptJupyterKernel    | kernelId, operationId.                                       | An executionId for the explicit interruption request.                                                       |
| RestartJupyterKernel      | kernelId, operationId.                                       | An executionId for restart completion; does not replay notebook cells.                                      |

Read the notebook with jupyter-view's MCP tools before running a cell or notebook. Pass its notebookId and opaque revision as expectedRevision, and select a kernel already bound to that notebook. To use an existing kernel with a newly created or unbound notebook, call BindJupyterNotebookKernel with an ID from ListJupyterKernels and wait for its execution receipt; use the resulting binding.revision in the next run request. Binding updates the usual kernelspec metadata and refuses replacing a busy or executing binding. Binding the same kernel does not change metadata or revision. It never starts, provisions or selects an interpreter for you. Notebook execution uses stable cell IDs and captured source; later reordering is safe, while a changed, deleted, closed or rebound cell is refused before dispatch. The captured code is limited to 1000 cells and 1,048,576 characters; RunJupyterCell captures only the requested cell, and RunJupyterNotebook excludes Markdown and raw cells. Arbitrary code is limited to 262,144 characters.

Every mutating call requires a new operationId, preferably a UUID. Retrying the same operationId with identical arguments returns the original receipt. Different arguments produce an operation_conflict and submit no code. Acceptance reserves the operation before source synchronization can yield, so concurrent retries do not create multiple executions. A rejected preparation returns accepted: false with a structured error and executionId.

Receipts survive package deactivation and module reload in the same window. An interrupted connection or unknown execution outcome never triggers a retry or cell replay. A deliberately new run needs a new operationId. The ledger retains at most 200 result records and 5000 operation receipts; evicting a result does not permit its operation to execute again, and a full receipt ledger refuses new operations. Closing the window ends this ledger.

Executions report queued, running, done or error. Completion follows the normal kernel pipeline's shell reply and trailing idle. A response can therefore already be terminal for a fast execution. Each result has a version for progress observation. GetJupyterExecution waits at most 10 seconds for a change, with at most eight pending execution observations per provider; additional waits return too_many_waits without allocating another timer. Observation timeout, cancellation and provider teardown release the wait quota and do not interrupt kernel work. Interruption and restart are separate explicit tools and affect the entire kernel, including human work sharing it. An interruption receipt confirms that the request was issued, not that Python stopped or that its side effects were undone.

MCP results contain at most 64 output summaries and 16,384 characters of text, with bounded traceback and MIME metadata. Images, HTML, JavaScript and binary MIME payloads are rendered through the normal UI rather than copied into tool responses. clear_output follows the current execution's output area, and notebook batches retain other cells' summaries. Retained state is plain data; callbacks, timers, kernels and adapters are disposed with the provider, and old tool objects cannot operate on a later package generation.
